# 📊 발표 주제: Jira 9 & 10 듀얼 호환성 확보 전략 (Single Source, Dual Build)

---

## 1. 인트로: 변화와 도전 과제

**[슬라이드 1: 타이틀 및 개요]**

* **제목:** Jira 10 마이그레이션 대응 전략
* **부제:** Single Source, Dual Build (단일 소스로 두 마리 토끼 잡기)
* **핵심 키워드:** Platform 7, Jakarta EE, Maven Profile
* **이미지:** Jira 9(Java EE)와 Jira 10(Jakarta EE) 사이의 끊어진 다리, 그리고 이를 연결하는 하나의 코드베이스 그림

**[🗣️ 발표 스크립트]**

> "안녕하세요. 다들 아시다시피, Atlassian이 Jira 10을 출시하면서 기반 플랫폼인 Platform 7을 도입했습니다. 이는 단순한 버전 업그레이드가 아닙니다. 기존 `javax` 패키지가 `jakarta` 패키지로 전면 교체되는, 사실상 생태계 자체가 바뀌는 변화입니다.
> 이로 인해 우리는 딜레마에 빠졌습니다. 'Jira 9용 코드와 10용 코드를 따로 관리해야 하나?' 프로젝트를 두 개로 쪼개면 유지보수 비용은 2배가 됩니다. 그래서 오늘은 소스 코드는 하나로 유지하면서, 빌드만 다르게 수행하여 두 버전을 완벽히 지원하는 **'Single Source, Dual Build'** 전략에 대해 말씀드리겠습니다."

---

## 2. 전략의 핵심: 물리적 분리

**[슬라이드 2: 프로젝트 구조 설계]**

* **도식:** 폴더 구조 다이어그램
* 📦 `src/main/java` (90%) : 비즈니스 로직 (Common)
* 📂 `src/main/jira9` (5%) : `javax.*` 어댑터
* 📂 `src/main/jira10` (5%) : `jakarta.*` 어댑터


* **텍스트:**
* **Common:** 버전과 무관한 순수 자바 로직 (DTO, Util, Interface)
* **Adapter:** 컴파일 에러가 발생하는 의존성 주입, REST Controller 분리



**[🗣️ 발표 스크립트]**

> "핵심 전략은 '문제가 되는 놈만 격리한다'입니다.
> 전체 코드의 90% 이상을 차지하는 비즈니스 로직은 `src/main/java`에 그대로 둡니다. 대신, `javax`와 `jakarta` 패키지 충돌이 일어나는 부분, 즉 서블릿 필터나 REST 컨트롤러 같은 진입점만 `jira9`과 `jira10` 폴더로 물리적으로 분리했습니다.
> 이렇게 하면 핵심 로직은 한 번만 수정해도 두 버전에 모두 반영되므로, 유지보수 효율성이 극대화됩니다."

---

## 3. 구현 방법: Maven Profile & Build Helper

**[슬라이드 3: Maven 빌드 프로세스]**

* **코드 스니펫:** `pom.xml`의 Profile 설정 일부
* **흐름도:**
1. `mvn package -Pjira9` 실행 → `src/main/java` + `src/main/jira9` 합체 → **Jira 9 OBR 생성**
2. `mvn package -Pjira10` 실행 → `src/main/java` + `src/main/jira10` 합체 → **Jira 10 OBR 생성**



**[🗣️ 발표 스크립트]**

> "이 구조를 가능하게 하는 엔진은 Maven Profile입니다.
> 보시는 것처럼 `jira9` 프로파일을 선택하면 Maven은 `src/main/jira9` 폴더를 소스 경로로 인식하고, `javax` 라이브러리를 가져옵니다. 반대로 `jira10` 프로파일을 선택하면 `src/main/jira10` 폴더와 `jakarta` 라이브러리를 사용합니다.
> 개발자는 복잡한 설정 신경 쓸 필요 없이, 빌드 명령어 뒤에 `-Pjira9` 또는 `-Pjira10` 옵션만 붙이면 됩니다."

---

## 4. 코드 패턴: 인터페이스 추상화

**[슬라이드 4: 코드 구현 패턴 (Bridge Pattern)]**

* **도식:**
* Caller (Common) ➡️ **Interface** (Common)
* **Interface** ⬅️ implements ⬅️ `Impl_Jira9` (Use javax.inject)
* **Interface** ⬅️ implements ⬅️ `Impl_Jira10` (Use jakarta.inject)


* **코드 예시:**
* `src/main/java/MyService.java` (Interface)
* `src/main/jira9/.../MyServiceImpl.java` (@Named, @Inject - javax)
* `src/main/jira10/.../MyServiceImpl.java` (@Named, @Inject - jakarta)



**[🗣️ 발표 스크립트]**

> "그렇다면 실제 코딩은 어떻게 할까요? 바로 '인터페이스'를 활용하는 것입니다.
> 공통 영역에 있는 서비스들은 구체적인 구현체 대신 인터페이스만 바라봅니다. 그리고 실제 구현체는 각 버전 폴더에 만들어 둡니다.
> 9버전 구현체는 `javax.inject`를 쓰고, 10버전 구현체는 `jakarta.inject`를 씁니다. 하지만 공통 영역에서는 이 차이를 전혀 알 필요가 없습니다. 런타임에 알아서 맞는 구현체가 주입되기 때문입니다."

---

## 5. 주의사항 및 체크리스트

**[슬라이드 5: 마이그레이션 체크리스트]**

* **표 (Table):** 분리 대상 및 주의사항
* **필수 분리:** Servlet, REST API, DI(Inject), JAXB(XML)
* **라이브러리 제거:** Atlassian Fugue (삭제됨), Log4j 1.x (삭제됨)
* **버전 변경:** Spring 6.x 호환성, Java 17 필수 (Jira 10 빌드 시)



**[🗣️ 발표 스크립트]**

> "물론 주의할 점도 있습니다. 단순히 패키지 이름만 바뀌는 게 아닙니다.
> `Atlassian Fugue` 같은 오래된 라이브러리는 아예 삭제되었습니다. 이런 것들은 Java 표준 라이브러리(`Optional` 등)로 교체 작업을 선행해야 합니다. 또한, Jira 10 빌드는 반드시 Java 17 환경에서 수행되어야 한다는 점도 CI/CD 구성 시 유의해야 합니다."
